# ADR 0007 — TDD, et cinq suites qui ne se recouvrent pas

**Statut** : accepté · **Date** : 2026-09-08

## Contexte

Un produit Stramatel se vérifie mal après coup : il parle à un pupitre, une horloge, un panneau
LED. Un défaut découvert à la mise en service coûte un déplacement ; découvert pendant un match,
il coûte le produit.

Les audits de la gamme le montrent : ce qui n'est pas couvert par un test finit par être vérifié
à la main sur un équipement, une fois, puis plus jamais. Les six points laissés ouverts sur le
G552 sont exactement de cette nature — ils demandent une machine parce que rien ne les couvre.

## Décision

**Le test vient avant le code**, et cinq suites se partagent le travail sans se recouvrir.

| Suite | Environnement | Couvre | Ne touche pas |
|---|---|---|---|
| `test:transport` | Node | codec de trames, ordonnanceurs, état, configuration | socket, port, base, DOM |
| `test:frames` | Node | décodeurs des data-modules | tout le reste |
| `test:unit` | jsdom | composants, schémas, hooks | base, réseau |
| `test:integration` | Node | gestionnaires de route, middleware, transports, **vraie base SQLite** | navigateur |
| `test:e2e` | Playwright | parcours complet sur le serveur réel | — |

### Ce qui n'est pas négociable

**L'intégration touche une vraie base.** Base SQLite jetable créée par
`tests/integration/global-setup.ts`, schéma poussé par Prisma, remise à zéro entre les tests.
Simuler Prisma prouverait le code du test, pas le schéma — ni les contraintes, ni les index
uniques. C'est précisément ce que l'intégration doit couvrir : le G552 n'a pas de contrainte
d'unicité sur `username`, et c'est de là que viennent ses comptes en double.

**Le matériel est simulé au niveau du paquet, jamais plus haut.** Les tests série remplacent
`serialport` ; tout ce qui est au-dessus — réassemblage, resynchronisation, dispatch, reprise —
est du vrai code exécuté. Simuler le transport lui-même ne prouverait rien.

**Un seuil de couverture qui échoue.** `lines 88 · statements 85 · functions 82 · branches 80`.
Sans plancher, la couverture baisse à chaque fonctionnalité ajoutée. Le seuil se relève quand une
fonctionnalité est portée, **jamais ne se baisse**.

**Ce qui est exclu de la mesure est nommé et justifié** : uniquement l'amorçage
(`server/index.mjs`, `src/i18n/request.ts`, `layout.tsx`, `page.tsx`), qui n'a pas de logique
propre et ne s'exerce qu'en démarrant le serveur. Toute logique qu'on serait tenté d'y ajouter
doit sortir dans un module testable.

## Une fonctionnalité n'est pas finie sans

1. des tests **unitaires** de sa logique pure — écrits avant elle ;
2. des tests d'**intégration** de ses routes et de son schéma, sur la vraie base ;
3. un **cas de refus** pour chaque contrôle d'accès qu'elle introduit ;
4. la couverture globale **au-dessus du plancher**, sans avoir baissé le plancher.

Le point 3 mérite d'être isolé : un test qui vérifie qu'une route fonctionne ne prouve pas
qu'elle refuse. Le middleware a huit cas de refus pour deux cas de passage.

## Ce que ça a déjà rapporté

Trois défauts trouvés par les tests **avant** toute mise en service, le jour de leur écriture :

| Défaut | Trouvé par |
|---|---|
| `@hookform/resolvers` v3 incompatible avec Zod 4 — **la validation du formulaire de connexion ne s'exécutait pas** | test unitaire du `LoginForm` |
| `sendUdp` ne pouvait émettre que vers son propre port d'écoute | test d'intégration UDP |
| Le lecteur série inondait le journal — une erreur toutes les 2 s, indéfiniment | démarrage réel, corrigé puis couvert |

Le premier est le plus parlant : le formulaire *paraissait* fonctionner. Sans le test, le défaut
serait parti en production.

## Conséquences

- Le pipeline a trois étages de test : `test:pur`, `test:integration`, `test:couverture`. Les
  trois sont bloquants et `package:docker` en dépend.
- Une correction de bogue commence par un test qui échoue et qui reproduit le bogue.
- `pnpm verify` enchaîne lint, typecheck et tests avant tout envoi.
